## Завдання 1. Загальний опис принципів проєктування

**Принципи проєктування програмного забезпечення** — це набір рекомендацій та правил, які допомагають розробникам писати чистий, зрозумілий код, який легко підтримувати, тестувати та масштабувати. 

Найбільш відомі загальні принципи:

* **KISS (Keep It Simple, Stupid)** — код має бути максимально простим. Не потрібно ускладнювати там, де можна зробити просто.
* **DRY (Don't Repeat Yourself)** — не повторюйся. Якщо один і той самий шматок коду використовується кілька разів, його треба винести в окрему функцію або клас.
* **YAGNI (You Aren't Gonna Need It)** — не пиши код для функцій, які «можливо, колись знадобляться». Вирішуй тільки поточні задачі.
* **SOLID** — п'ять базових принципів об'єктно-орієнтованого програмування.

## Завдання 2. Детальний опис одного із принципів SOLID 

Для прикладу розглянемо перший принцип SOLID — **Single Responsibility Principle (SRP)** або **Принцип єдиної відповідальності**.

**Опис:** Кожен клас повинен мати лише одну причину для зміни. Тобто клас має виконувати лише одне конкретне завдання (мати одну зону відповідальності). Якщо клас робить занадто багато речей одночасно, його важко змінювати.

### Приклад коду на Python

Спочатку подивимось, як **НЕ треба** робити (порушення принципу). Клас `User` тут зберігає дані користувача і сам же відповідає за їх збереження у файл.

```python
# ПАГАНИЙ ПРИКЛАД (Порушення SRP)
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email

    def get_info(self):
        return f"Користувач: {self.name}, Email: {self.email}"

    # Цей метод порушує принцип! 
    # Клас User не повинен займатися роботою з файлами.
    def save_to_file(self):
        with open(f"{self.name}.txt", "w", encoding="utf-8") as f:
            f.write(self.get_info())

```

Тепер перепишемо код **правильно**. Ми розділимо логіку на два класи: один відповідає лише за дані користувача, а інший — лише за збереження даних.

```python
# ХОРОШИЙ ПРИКЛАД (Дотримання SRP)

class User:
    """Клас відповідає лише за збереження даних користувача."""
    def __init__(self, name, email):
        self.name = name
        self.email = email

    def get_info(self):
        return f"Користувач: {self.name}, Email: {self.email}"


class FileManager:
    """Клас відповідає лише за роботу з файлами."""
    @staticmethod
    def save_user_to_file(user):
        filename = f"{user.name}.txt"
        with open(filename, "w", encoding="utf-8") as file:
            file.write(user.get_info())
        print(f"Дані успішно збережено у {filename}")


# Перевірка роботи коду:
if __name__ == "__main__":
    student = User("Олександр", "alex@example.com")
    
    # Використовуємо окремий клас для збереження
    FileManager.save_user_to_file(student)

```

**Чому це краще?** Якщо ми захочемо зберігати дані не у файл, а в базу даних (або виводити їх на веб-сторінку), ми просто створимо новий клас для збереження, а сам клас `User` чіпати не доведеться.

## Запитання для самоконтролю

### 1. Що таке принципи проєктування? Які принципи Вам відомі?

**Відповідь:** Принципи проєктування — це набір кращих практик, які допомагають створювати гнучку та надійну архітектуру програми. Вони зменшують заплутаність коду.
Крім SOLID, мені відомі такі принципи як **DRY** (не повторюйся), **KISS** (роби простіше) та **YAGNI** (не роби того, що поки не потрібно).

### 2. Що таке принципи SOLID? Опишіть відомі Вам принципи детальніше.

**Відповідь:** SOLID — це акронім, який об'єднує 5 основних принципів об'єктно-орієнтованого програмування:

1. **S (Single Responsibility)** — Принцип єдиної відповідальності. Клас має робити лише одну річ.
2. **O (Open/Closed)** — Принцип відкритості/закритості. Програмні сутності мають бути відкриті для розширення, але закриті для зміни (новий функціонал додаємо новим кодом, а не переписуємо старий).
3. **L (Liskov Substitution)** — Принцип підстановки Барбари Лісков. Об'єкти батьківського класу можна замінити об'єктами класу-нащадка без поломки програми.
4. **I (Interface Segregation)** — Принцип розділення інтерфейсу. Краще створити кілька вузькоспеціалізованих інтерфейсів, ніж один універсальний, який змушує реалізовувати непотрібні методи.
5. **D (Dependency Inversion)** — Принцип інверсії залежностей. Класи верхнього рівня не повинні залежати від класів нижнього рівня; обидва повинні залежати від абстракцій.
